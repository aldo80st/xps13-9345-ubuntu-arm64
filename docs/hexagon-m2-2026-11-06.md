## Incidente de la primera prueba real — 2026-11-06

### Prueba 1, 23:11:16 UTC: acceso a dispositivo concedido

El usuario ejecutó `sudo setfacl -m "u:$(id -un):rw" /dev/fastrpc-cdsp /dev/dma_heap/system` desde terminal local. La comprobación mediante `getfacl` y `os.access` confirmó permisos efectivos. Se intentó inferencia con GenieX 0.10.0, QAIRT 2.50, `qualcomm/Qwen3-0.6B:w4a16`, `--compute npu` (sin CPU fallback). Falló al abrir transporte con `0x80000580` y `14001`: ningún token generado.

### Corrección de descubrimiento FastRPC en el laboratorio

El build de FastRPC usa `CONFIG_BASE_DIR=$HOME/labs/xps13-9345-hexagon/install/qcom`. No existía el mapeo YAML bajo `conf.d`, y la variable de rutas inicial empleaba separador `:` en lugar de `;`. Se creó **únicamente en el home de usuario**, sin operaciones administrativas:

```yaml
machines:
  Dell XPS 13 9345:
    DSP_LIBRARY_PATH: dsp
    CDSP_ARCH: v73
```

Se crearon enlaces simbólicos de los 17 ELF ya admitidos y `libQnnHtpV73Skel.so` bajo `install/qcom/dsp/cdsp`. FastRPC confirmó en el journal de usuario `dsp_lib_paths is dsp` y `YAML arch for domain 3 ... v73`. La solución coincide con el mecanismo de búsqueda del código oficial: el shell inicial se localiza en `CONFIG_BASE_DIR/conf.d`, no solo mediante `ADSP_LIBRARY_PATH`.

### Prueba 2, 23:13:41 UTC: fallo fatal del CDSP

Se reintentó la misma inferencia QAIRT/NPU, con la ruta YAML correctamente resuelta. El error original `0x80000580` dejó de ser el resultado principal. QNN reportó `createUnsignedPD unsigned PD or DSPRPC_GET_DSP_INFO not supported by HTP`, `openSessionForPriority failed ... 0x00000072`, seguido de `14001`. El journal kernel registra exactamente a esa hora:

```text
qcom_q6v5_pas 32300000.remoteproc: fatal error received: sleep_statsi.c:537:
remoteproc remoteproc1: crash detected in cdsp: type fatal error
remoteproc remoteproc1: handling crash #1 in cdsp
remoteproc remoteproc1: recovering cdsp
remoteproc remoteproc1: stopped remote processor cdsp
remoteproc remoteproc1: remote processor cdsp is now up
```

**NPU no ejecutó inferencia.** El kernel recuperó automáticamente el CDSP sin reinicio manual ni cambios de firmware. La recuperación recreó `/dev/fastrpc-cdsp`, eliminando su ACL temporal; `/dev/dma_heap/system` conservó la ACL. En la última comprobación, CDSP y ADSP aparecen `running`, Ollama CPU continúa activo.

### Evaluación de seguridad y siguientes puertas

El nodo `/sys/class/remoteproc/remoteproc1/device/power/control` indica `auto`, pero `power/runtime_status` dice `unsupported`: **no está demostrado que runtime PM sea la causa específica**. Un [caso técnico de Snapdragon X Elite](https://docs.demain.technology/wiki/21-npu-runtime-safe-rust-wrappers-for-qualcomm-hexagon-fastrpc/) menciona el mismo `sleep_statsi.c:537` y apunta a administración de energía, pero requiere revisión de compatibilidad Dell/kernel antes de aplicar cambios.

**STOP/NO-GO:** No repetir llamadas QNN a la NPU, alterar `remoteproc`, Secure Boot, firmware, kernel, servicios privilegiados o controles PM sin un diagnóstico y mitigación controlada. El script `hexagon-m2-smoke.sh infer` exige ahora `CONFIRM_CDSP_CRASH_RISK=YES` de forma explícita y valida el mapeo YAML; no se aconseja configurar esa variable hasta evaluar la caída. El PR continúa en borrador, sin merge, y el hito sigue **NO completado**.

**Precisión sobre la causa:** la lectura del YAML sí está probada por el journal, pero **no hay registro de que la carga de `fastrpc_shell_unsigned_3` ni del skel QNN haya culminado**. El fallo de dispositivo `ENODEV` ocurrió durante la caída del CDSP; no atribuirlo exclusivamente al shell, a permisos ni a runtime PM sin pruebas adicionales. El CDSP se recuperó por la política de `remoteproc` (`recovery=enabled`).
